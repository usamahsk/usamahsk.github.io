Testing Basics

Code that checks your code — so changes stop being scary.

1 · Readthe concept
2 · Watcha test run
3 · Practiceget checked
4 · Provesay it out loud
In plain words A test is a small program that calls your code with known input and checks the output against what you promised. Its superpower isn't catching today's bug — it's that tomorrow, when someone changes the code, the test tells them instantly if they broke the promise. Tests turn "I hope nothing broke" into "the suite is green."

1.Read the concept

Anatomy of a test — given, when, then

// with vitest / jest — the two dominant runners, near-identical APIs
describe("slugify", () => {
  it("turns a title into a URL-safe slug", () => {          // the PROMISE, in words
    expect(slugify("  Hello World!  ")).toBe("hello-world"); // known in → expected out
  });

  it("collapses repeated spaces", () => {
    expect(slugify("hello    world")).toBe("hello-world");
  });

  it("handles empty input", () => {                          // the EDGE CASE
    expect(slugify("")).toBe("");
  });
});
// each `it` is independent: fresh setup, one behavior, clear failure message

Read the test names aloud — they read like documentation: "slugify turns a title into a URL-safe slug." That's the first mindset shift: tests are executable specifications. When the suite passes, those sentences are true; when one fails, a sentence about your program just became false, and you know exactly which.

Unit vs integration — the pyramid in one screen

  • Unit tests — one function/module in isolation, fast (milliseconds), hundreds of them. slugify("x") with no network, no DOM. The base of the pyramid.
  • Integration tests — several pieces working together: your function + real database, or two modules interacting. Slower, fewer. They catch what units can't: the pieces fit but the seams leak.
  • End-to-end (E2E) — a robot using the real app in a real browser (clicking, typing). Slowest, rarest, closest to the user's reality.

The pyramid shape is the guidance: many unit tests, some integration, a few E2E — because cost grows and speed shrinks as you climb. A suite that's all E2E takes 40 minutes and breaks for cosmetic reasons; a suite that's all units can pass while the app is completely broken.

What separates good tests from theater

  • Test behavior, not implementation. Assert "the cart totals 30" — not "the internal calculate method was called with 3." Implementation tests shatter on every refactor even when behavior is perfect; that's how teams learn to hate their test suite.
  • Each test is independent — no test may depend on another having run (or on shared mutable state). Order-dependent tests pass alone and fail together, randomly.
  • Test the edges on purpose: empty input, zero, negative, huge, missing fields, weird unicode. Bugs live at the edges; happy paths rarely crash.
  • Coverage is a thermometer, not a goal — 80% coverage with meaningless assertions is theater; a test that calls the code and asserts nothing raises coverage while proving nothing.

Exceptions & traps — the complete list

  • Testing implementation details — brittle tests that fail on every internal rename; test the observable contract instead.
  • Order-dependent tests — a test passing only because a previous one mutated shared state; each test must stand alone.
  • Async tests that never actually test — forgetting to await/return the promise makes the test "pass" instantly, before the assertion runs. The classic silent false-green.
  • Mocking everything — if every dependency is mocked, the test verifies your mocks talk to each other, not your code; mock boundaries (network, time), not internals.
  • Coverage worship — coverage measures what EXECUTED, not what was VERIFIED; assertion-free tests inflate it dishonestly.
  • Flaky tests stay red — a test failing intermittently (timing, dates, randomness) trains the team to ignore red; fix it or quarantine it deliberately, never ignore it.
  • Testing the framework — a test asserting React renders a div is testing React; test YOUR logic, mock the rendering boundary.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "A test is a program that calls my code with known input and asserts the expected output — and its real value is regression safety: change the code, and the suite tells you instantly which promises broke. I structure them given-when-then with names that read like documentation, keep each test independent, and deliberately test edges — empty input, zero, missing fields. I follow the pyramid: many fast unit tests, fewer integration tests across seams, a handful of E2E. And the discipline I care about most: test behavior, not implementation — implementation tests shatter on refactors and teach the team to ignore the suite."
