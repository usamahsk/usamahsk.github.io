npm & package.json

The plumbing of every JavaScript project — the part interviews assume you just know.

In plain words npm is the app store plus librarian for JavaScript: two million packages other people wrote, and a tool that downloads them, tracks which versions your project uses, and records it all in one file — package.json — your project's ID card.

1.Read the concept

The file that answers every question about the project

{
  "name": "my-app",
  "scripts": {
    "dev": "vite",                    // npm run dev → starts the dev server
    "build": "vite build",            // npm run build → production bundle
    "test": "vitest"
  },
  "dependencies": {                   // needed IN PRODUCTION (the app itself)
    "react": "^18.2.0",
    "axios": "^1.6.0"
  },
  "devDependencies": {                // needed only WHILE DEVELOPING
    "vitest": "^1.0.0",               // tests, bundlers, linters, formatters
    "eslint": "^8.50.0"
  }
}

The dependencies/devDependencies split is the standing interview question: dependencies ship to your users (React must exist in the final app); devDependencies are your workshop tools (the test runner and bundler do their job before deployment and never ship). Installing with npm install lodash adds to dependencies; npm install -D eslint adds to devDependencies.

Version numbers — the ^ and ~ decoded

"react": "^18.2.0"   // ^ = 18.x.x — minor + patch updates allowed (most common)
"axios": "~1.6.0"    // ~ = 1.6.x — patch updates only (more conservative)
"left-pad": "1.3.0"  // exact — nothing moves

// semver: MAJOR.MINOR.PATCH
// MAJOR = breaking changes (18 → 19 may break your code)
// MINOR = new features, backwards-compatible
// PATCH = bug fixes

^ is a promise: "18-to-18 won't break me" — trusting the library authors' semver discipline. It's also why package-lock.json exists: it freezes the exact versions everyone on the team gets, so your machine and CI install identical code. Commit it; never hand-edit it.

The commands and the folder nobody commits

npm install            // build node_modules from package.json + lock file
npm install lodash     // add a dependency (updates package.json + lock)
npm run dev            // run a script from "scripts"
npm test               // shortcut — "test" gets its own alias
npm uninstall lodash   // remove cleanly

node_modules — the folder where installed packages actually live — is never committed to git (it's enormous and can be rebuilt from the lock file with one npm install). That's why it's in every .gitignore: the lock file is the source of truth; the folder is disposable.

Exceptions & traps — the complete list

  • Commit package-lock.json, never node_modules — the lock guarantees identical installs across machines; the folder is 300MB of rebuildable stuff.
  • A dependency in the wrong section "works" — until it doesn't — dev tooling in dependencies bloats production installs; production code in devDependencies breaks other people's builds.
  • npm ci vs npm install — ci installs exactly the lock file (fast, strict, for CI pipelines); install can update within semver ranges.
  • ^ can still break you — semver is a promise by library authors, and they break it sometimes; the lock file is your seatbelt.
  • Two packages need different majors of the same library — you get both (nested installs), and "works on my machine" bugs are born here. Major upgrades deserve a test run.
  • Scripts are just shell commands — npm run anything runs whatever you define; npm also adds node_modules/.bin to the PATH so locally-installed CLIs work without global installs.
  • Global installs (-g) are for tools, not project deps — a project depending on a globally-installed package works on your machine and nowhere else.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "package.json is the project's ID card: metadata, scripts, and two dependency sections — dependencies ship to production, devDependencies are workshop tooling like test runners and bundlers. Versions follow semver: major is breaking, minor adds features, patch fixes bugs — and the ^ I see everywhere means 'any 18.x', which is why package-lock.json exists: it freezes exact versions so every machine installs identically. It gets committed; node_modules doesn't — it's rebuildable with one npm install. And npm ci is the strict lock-file install used in CI pipelines."

The file → the split → semver → the lock discipline. Four beats, all professional-grade.
