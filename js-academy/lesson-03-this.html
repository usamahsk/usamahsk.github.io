The this Keyword

Decided by how a function is called — never by where it is written.

1 · Readthe concept
2 · Watchthe rule picker
3 · Practiceget checked
4 · Provesay it out loud
In plain words this is not decided when you write the function — it's decided at the moment someone calls it. Look at the call: is there a dot before it? A new? Nothing at all? Each shape gives a different answer. Arrow functions are the exception: they take this from the code around them, like any other variable.

1.Read the concept

The reason this feels chaotic is that people look in the wrong place. It's not defined by the function's code, its position in the file, or the object it's attached to. It's defined by one question about the moment of calling: how exactly was this function invoked? There are four shapes of invocation — four rules — plus the arrow exception. Learn to classify the call, and this becomes mechanical.

Rule 1 — Plain call: fn()

function who() {
  console.log(this);
}

who();        // no dot, no new, no bind

this is: undefined (strict mode / modules) — or window in loose scripts

Nothing anchors the call, so there is no this. Most mysterious "why is this undefined?" bugs are this rule in disguise — usually a method that got detached from its object before being called (you'll see that trap in the practice section).

Rule 2 — Method call: obj.fn()

const user = {
  name: "Sam",
  hi() { console.log("Hi, " + this.name); }
};

user.hi();    // there is a DOT — and whatever is LEFT of it becomes this

this is: user → prints "Hi, Sam"

Read the call site left-to-right: the object before the dot wins. The same function attached to two different objects produces two different this values — proof that the function doesn't own its this; the call lends it.

Rule 3 — Explicit: call, apply, bind

function greet(city) {
  console.log(this.name + " from " + city);
}

const u = { name: "Sam" };

greet.call(u, "Berlin");       // this = u, args one by one
greet.apply(u, ["Berlin"]);    // this = u, args as an array
const bound = greet.bind(u);   // returns a NEW function,
bound("Berlin");               // permanently locked to u

this is: u — every time

Use these when you must force a this. The everyday hero is bind: whenever you hand a method to something else — a timer, an event listener, forEach — the method loses its object, and bind reattaches it.

Rule 4 — Constructor: new Fn()

function Person(name) {
  this.name = name;     // this = the object new just built
}

const p = new Person("Sam");
p.name;                 // "Sam"

this is: the brand-new object

new performs four steps: create an empty object, link its prototype, run the function with this pointing at that object, and return it. This is the bridge to the prototypes lesson.

The exception — arrow functions

const timer = {
  seconds: 0,
  start() {                       // regular method: this = timer
    setInterval(() => {           // arrow — WRITTEN inside start()
      this.seconds++;             // inherits start()'s this → works
    }, 1000);
  }
};

Arrows don't follow the four rules at all. Like any other variable, they close over this from the scope where they were written — which, notice, makes them a closure over this (lesson 2 again). Perfect for callbacks that need the surrounding this; wrong for object methods that need their own.

Priority when rules collide new beats bind/call/apply, which beat obj.method(), which beats a plain call. Arrows are outside the competition — they never get their own this in the first place. Recite this order once and you can answer any "which rule wins?" question.

Exceptions & traps — the complete list

  • The detached-method trap: const h = obj.hi; h() — the dot is gone, this is undefined/window. The function is identical; only the call changed.
  • Strict vs loose: a plain call gives undefined in modules/strict mode, window in loose scripts — same code, two answers depending on mode.
  • Arrows inherit — they never get their own: an arrow method in an object literal takes this from outside the object, not from the object.
  • Callback detachment: forEach(cart.add) calls add as a plain function — this.total is never the cart. Fix: cart.add.bind(cart) or n => cart.add(n).
  • Priority order: new beats bind/call/apply, which beat obj.method(), which beats plain call. new boundFn() ignores the binding entirely.
  • call vs apply: identical except argument shape — call(obj, a, b) vs apply(obj, [a, b]). Mixing them up silently breaks arguments.
  • bind returns a NEW function — calling obj.fn.bind(x) doesn't change obj.fn; you must use the returned copy.
  • Arrow in setInterval works, function(){} breaks — the arrow keeps the method's this; the regular function drops it (plain-call rule inside the callback).

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "this is set at the call site by the shape of the invocation. Four rules in priority order: a plain call gives undefined or window; obj.method() gives the object before the dot; call, apply and bind set it explicitly, with bind returning a permanently bound copy; and new gives the freshly built object. Arrow functions have no own this — they inherit it from the scope where they're written, which is exactly why I use them for callbacks like setInterval inside a method, and why the detached-method bug happens: assign obj.hi to a variable, call it plain, and the dot is gone."

Notice the structure: rules → arrows → a real bug story. Interviewers remember the bug story.
