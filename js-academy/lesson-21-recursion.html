Recursion

A function that calls itself — and the one rule that stops it from never stopping.

1 · Readthe concept
2 · Watchthe stack
3 · Practiceget checked
4 · Provesay it out loud
In plain words Recursion is solving a big problem by solving a smaller copy of the same problem — until you hit a version so small the answer is obvious. Every recursive function needs exactly two things: a base case ("this is so small I can answer directly") and a recursive case ("reduce the problem and call myself on it").

1.Read the concept

Build it from what you know

Factorial: 5! = 5 × 4 × 3 × 2 × 1. The loop version counts down and multiplies. But notice a different way to say it: 5! is 5 × 4!. And 4! is 4 × 3!. Every factorial is the current number times the factorial of one less — the problem contains smaller copies of itself:

function factorial(n) {
  if (n <= 1) return 1;                 // BASE CASE: obvious, no self-call
  return n * factorial(n - 1);          // RECURSIVE CASE: smaller problem + me
}

factorial(5);   // 120

Two lines, two jobs. The base case is the emergency brake — without it, the function calls itself forever and the call stack overflows. The recursive case must always move toward that brake (n - 1 gets smaller every time). Miss either half and it breaks: no base case → crash; a case that doesn't shrink → crash.

What actually happens in memory

Each call gets its own frame on the call stack — its own n, its own position to return to. factorial(3) stacks up three frames, then unwinds as answers flow back down. The stack has a size limit (~10,000 frames in browsers) — which is where the famous crash comes from:

function broken(n) { return n * broken(n - 1); }   // no base case!
broken(5);   // 💥 RangeError: Maximum call stack size exceeded

Where recursion genuinely earns its place

Loops handle flat lists. Recursion handles shapes that contain themselves — and that's not a riddle, it's real data:

// a comment thread: replies have replies have replies…
const thread = {
  text: "root",
  replies: [
    { text: "reply A", replies: [ { text: "A-1", replies: [] } ] },
    { text: "reply B", replies: [] },
  ],
};

function countAll(node) {
  let total = 1;                                   // count me
  for (const reply of node.replies) {
    total += countAll(reply);                      // …and everything inside me
  }
  return total;
}
countAll(thread);   // 4 — no matter how deep the nesting goes

Try writing that with a loop: you'd need a loop inside a loop inside a loop, with no way to know the depth in advance. Recursion doesn't care how deep it goes — "count me, then let recursion handle everything inside me." Same power for file trees, JSON structures, menus, org charts: any tree.

Exceptions & traps — the complete list

  • Missing base case = RangeError: Maximum call stack size exceeded — the #1 recursion crash; every recursive path must reach the brake.
  • Base case that's never reached — same crash, subtler: if (n === 0) with n - 2 steps from odd numbers skips right past 0 forever.
  • Forgetting to return the recursive call — f(n - 1); instead of return f(n - 1); — the answer dissolves into undefined on the way back up.
  • Stack depth limit (~10k frames in browsers) — deep linear recursion (summing a 100k-long list) overflows; loops are the right tool for linear problems.
  • Same subproblem computed twice — naive fib(n) re-computes fib of the same numbers exponentially many times; memoize (the closure lesson!) to fix it.
  • Mutation shared across calls — passing an array down and pushing into it in one branch surprises other branches; build fresh values upward instead.
  • Every call costs a stack frame — recursion is elegant for trees, wasteful for counting; choose by the data's shape, not by style points.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "Recursion solves a problem by solving a smaller copy of itself, and every recursive function needs two parts: a base case that answers directly, and a recursive case that shrinks the problem toward that base case. Each call gets its own frame on the call stack, which is why a missing base case ends in 'maximum call stack size exceeded'. I reach for recursion when data is tree-shaped — comment threads, file systems, nested JSON — because a loop would need to know the depth in advance, and recursion doesn't care. For linear problems I use loops, and when the same subproblem repeats I memoize with a cache."

Two parts → stack → crash → when it earns its place → the memoize upgrade. Complete.
