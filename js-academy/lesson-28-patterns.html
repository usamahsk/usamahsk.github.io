Design Patterns

Named solutions to problems every codebase meets — the vocabulary of code reviews and architecture talks.

1 · Readthe concept
2 · Watchthe observer

In plain words A design pattern is a solution to a recurring problem, given a name so teams can discuss it in one word. "Use an observer here" transfers an entire design in two words. Interviews rarely ask you to recite the GoF book — they ask "name a pattern you've used and why," which is a storytelling question: one pattern, known deeply, beats ten recited.

1.Read the concept

The four patterns you can honestly claim

// 1. MODULE — private state + public API (your closures lesson, promoted)
function makeCart() {
  let items = [];                              // private
  return {
    add: (item) => items.push(item),
    total: () => items.length,
  };
}
const cart = makeCart();   // items is unreachable from outside
// 2. SINGLETON — exactly one instance, shared everywhere
const config = {
  apiUrl: "https://api.myapp.com",
  features: { darkMode: true },
};
export default config;      // module code runs ONCE (modules lesson!) —
                            // every importer receives the SAME object
// 3. FACTORY — functions that build objects, customized
function makeUser(name, role = "member") {
  return { name, role, createdAt: Date.now(), greet() { … } };
}
const admin = makeUser("Sam", "admin");
// 4. OBSERVER — "notify me when X happens" (you know it as events)
subject.addListener(fn);     // subscribe
subject.emit(data);          // everyone subscribed gets called
// addEventListener IS the observer pattern, built into the browser

Notice something: you've used all four. The module pattern is your closures lesson with a business title. The singleton is your modules lesson (module code runs once). The factory is a function returning objects — the multiplier/makeCounter family from closures. The observer is addEventListener. Design patterns aren't new machinery — they're names for moves you already know, which is exactly why the honest interview answer works: pick one, tell where you used it, and what problem it solved.

The interview conversation, mapped

  • "Which patterns have you used?" → Module (closures for private state), Observer (event-driven UI), Singleton (shared config/API client), Factory (test-data builders). Pick one and go deep.
  • "Why patterns at all?" → Shared vocabulary + proven structure: they prevent each developer from inventing a private dialect for the same problem.
  • "Any downside?" → Overengineering. Patterns applied without the problem they solve add layers, not clarity. The pattern serves the problem — never the reverse.

Exceptions & traps — the complete list

  • Overengineering is the classic failure — a Singleton "because it's a pattern" on data that could be a plain export; patterns solve problems, they're not badges.
  • JS singletons are usually just modules — module code runs once, so a plain exported object IS the singleton; a class with getInstance() is often ceremony for ceremony's sake.
  • Module pattern vs modern classes: closures give hard privacy (truly unreachable state); class private fields (#x) do the same natively now — know both.
  • Observer leaks listeners — every subscribe is a reference (memory lesson!); unsubscribing on teardown is part of the pattern, not an optional extra.
  • Factories vs classes: factories are plainer and compose well; classes add inheritance and instanceof. Either is fine — inconsistency across a codebase is the real smell.
  • Names drift: "service", "manager", "helper", "store" — teams rename patterns constantly; recognizing the shape (private state? one instance? notify-many?) matters more than the label.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "The pattern I use most is the module pattern — a function returning an API over private closure state; my cart and counter utilities are exactly that, and it gives hard privacy for free. I also lean on the observer pattern constantly without naming it: addEventListener IS observer — subscribe, emit, many listeners get notified. And in JavaScript, singletons usually come free from modules, since module code runs once and every importer shares the same exported object. The one warning I take seriously is overengineering: a pattern earns its place by solving a problem I actually have, not by sounding senior."

One pattern, deep — the others named — and the overengineering caveat. That's the answer that sounds like experience.
