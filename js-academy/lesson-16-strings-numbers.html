Strings & Numbers

The daily-use methods — and the "5" + 3 trap that starts every coercion discussion.

1 · Readthe concept
2 · Watchthe playground
3 · Practiceget checked
4 · Provesay it out loud
In plain words Text in JavaScript behaves like printed paper: you can't erase a letter — every method hands you back a brand-new piece of paper, and the original stays exactly as it was. Numbers are all stored the same way (decimals included), which is mostly fine — until you meet 0.1 + 0.2 and the "5" + 3 trap.

1.Read the concept

Text and numbers — the material of every form field, every API response, every log line. Two values, used daily for six years. And both have a habit of refusing to do what you expected.

Strings can never change

let s = "hello";
s.toUpperCase();
console.log(s);        // "hello" — the method did NOTHING?!

toUpperCase() didn't change s because strings cannot change. The method built a brand-new string ("HELLO") and handed it back… to nobody. The result was never captured, so it evaporated. The fix is catching the new sheet:

s = s.toUpperCase();   // now s points at the new string

Strings are printed paper: you can't erase a letter, only print a new one. And chaining works because of this — s.trim().toUpperCase() only functions because each step returns a fresh sheet for the next step to grab.

The + / − asymmetry

console.log("5" + 3);  // "53" — plus sees a string and says "join them!"
console.log("5" - 3);  // 2    — minus forces both sides into numbers

+ has two jobs — add numbers, glue text — and when one side is text, it picks glue. - has only one job, so it drags both sides into numbers. Same values, opposite operators, opposite behavior. The defensive habit: convert on purpose, then do math — because everything from a form arrives as a string.

Now the definition makes sense Strings are immutable — every method returns a new string, which you must capture. + with any string means join, not add. Everything from users arrives as text — convert explicitly before math.

Conversions have personalities

parseInt("12px");     // 12   — lenient: reads digits, stops at "px"
Number("12px");       // NaN  — strict: the WHOLE string must be numeric
+"3.5";               // 3.5  — unary plus, the shorthand (same as Number)

(3.14159).toFixed(2); // "3.14"  ⚠️ a STRING — math needs Number() first
Number.isNaN(NaN);    // true — the only reliable NaN test

parseInt for "150px"-style values, Number for clean data. Meanwhile the string methods you'll use weekly — all following the immutable rule: trim(), slice(0, 3) (start included, end excluded), split(",") and join("-") (string ↔ array, the pair that reshapes everything), includes(), replaceAll(). And template literals replace all gluing: `Hi ${name}, you scored ${score}%` — expressions work inside ${ }, multi-line text comes free.

Exceptions & traps — the complete list

  • Immutability: every string method returns a new string — capture it: s = s.trim(). Uncaptured results evaporate.
  • slice(1, 4) excludes the end — positions 1, 2, 3. Negative indices count from the end: slice(-3) → last three characters.
  • "5" + 3 is "53", "5" - 3 is 2 — plus prefers joining; minus forces numbers.
  • Number("") is 0 — not NaN! Number(null) is also 0; only undefined and garbage text give NaN. Silent bug source.
  • parseInt("0.5") is 0 — it stops at the dot! For decimals use Number or parseFloat.
  • toFixed returns a string — and it can round "wrong" because of float storage: (1.005).toFixed(2) → "1.00".
  • replace replaces only the FIRST match — use replaceAll for all of them.
  • str[0] works but str[-1] is undefined — strings have no negative indexing; use str.at(-1) (modern) or slice(-1).
  • 0.1 + 0.2 !== 0.3 — float storage again; compare with a tolerance (Math.abs(a - b) < 0.001), or count money in integer cents.
  • Failed conversions give NaN — test with Number.isNaN(x), never x === NaN.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "Strings are immutable — every method returns a new string, so I capture results: s.trim().toUpperCase() chains because each step returns a fresh string. I reach for template literals over concatenation, slice with the end-exclusive rule, and the split-join pair for turning strings into arrays and back. Numbers are all 64-bit floats: Number converts strictly — '12px' becomes NaN — while parseInt parses until it can't and gives 12; toFixed looks numeric but returns a string; and the classic coercion trap is '5' + 3 giving '53' while '5' - 3 gives 2, because plus prefers concatenation. For anything from user input I convert explicitly before doing math."

Immutability → the daily methods → conversion trio → the + trap. All first-hand knowledge.
