Storage: localStorage, sessionStorage & Cookies

Three places to keep data in the browser — with three very different lifetimes and purposes.

In plain words localStorage is a small notebook the browser keeps forever — survive closing the tab, the browser, even rebooting. sessionStorage is a sticky note on one tab — dies with that tab. Cookies are notes that get mailed to the server with every request — which is their superpower and their size limit.

1.Read the concept

The API that everyone uses daily

localStorage.setItem("theme", "dark");   // save
localStorage.getItem("theme");           // "dark"
localStorage.removeItem("theme");        // delete one
localStorage.clear();                    // delete everything
// same API for sessionStorage — different lifetime

Three facts govern everything. One: both stores hold strings only — about 5MB each, per origin. Two: localStorage survives everything; sessionStorage dies when the tab closes. Three: neither is ever sent to the server — they're purely for your JavaScript. Cookies are the opposite on that last point, and that difference defines their job.

The trap that breaks everyone once

localStorage.setItem("user", { name: "Sam" });   // storing an object…
localStorage.getItem("user");                    // "[object Object]" 💩

// objects must travel as JSON text:
localStorage.setItem("user", JSON.stringify({ name: "Sam" }));
const user = JSON.parse(localStorage.getItem("user"));   // { name: "Sam" } ✓

The store coerced your object to a string — and the string form of a plain object is the useless "[object Object]". Round-trip everything structured through JSON.stringify / JSON.parse. And remember the parse trap: JSON.parse(null) throws — so a missing key needs a guard: JSON.parse(localStorage.getItem("user") || "null").

Cookies — different job, different rules

// set by the SERVER usually (Set-Cookie header), readable in JS via document.cookie
document.cookie = "theme=dark; max-age=86400; path=/";
document.cookie;              // "theme=dark; other=…" — one string, parsed by you

// the modern, secure way (server-side, HttpOnly — JavaScript can't touch it):
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax

Cookies are small (~4KB), expire on schedule, and — the defining feature — are attached automatically to every request to their domain. That's why sessions and logins live in cookies: the server needs to know who you are on every request, without your JS forwarding anything. HttpOnly makes the cookie invisible to JavaScript (stealing it via XSS becomes impossible — see the security lesson); SameSite limits cross-site sending (CSRF defense).

Choosing — the interview's real question

  • UI preferences, cached data, drafts → localStorage: needs to survive restarts, server never cares.
  • Multi-step form state, "in-progress" work → sessionStorage: dies with the tab, no cleanup needed.
  • Sessions, auth, anything the server must see → cookie (HttpOnly, Secure, SameSite): travels with every request.
  • Tokens? → the modern default is an HttpOnly cookie precisely because localStorage-stored tokens are readable by any injected script.

Exceptions & traps — the complete list

  • Strings only — storing an object yields "[object Object]"; storing a number gives "42" (a string back!). Always JSON round-trip structured data.
  • Missing keys return null — and JSON.parse(null) throws. Guard: JSON.parse(x || "null") or try/catch.
  • Quota is real (~5MB) — setItem throws QuotaExceededError when full; large data belongs in a database (IndexedDB), not here.
  • It's synchronous — every read/write blocks the main thread; megabytes of localStorage churn jank the UI.
  • localStorage is per-origin — localhost:3000 and localhost:3001 have separate stores (same rule as CORS lesson).
  • Never store secrets in localStorage — any XSS can read it (`localStorage.getItem("token")` is one line). HttpOnly cookies exist precisely because JS can't read them.
  • sessionStorage is per-TAB — a duplicated tab copies it; a new tab starts empty. Surprising in tests.
  • document.cookie is one noisy string — all cookies concatenated, no API for reading one; parse it yourself (or use a helper library).
  • Storage events — other tabs get a storage event when localStorage changes; the changing tab doesn't. A free cross-tab messaging channel.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "The browser gives me three stores. localStorage persists across restarts, holds ~5MB of strings per origin, and is never sent to the server — good for preferences and cached data. sessionStorage is the same API but dies with the tab. Cookies are small, expiring, and automatically attached to every request to their domain — which is why sessions live there, ideally as HttpOnly Secure cookies that JavaScript can't read, since localStorage tokens are one XSS away from stolen. The trap I always handle: the stores are string-only, so objects need JSON.stringify going in and a guarded JSON.parse coming out, because a missing key returns null and parsing null throws."

Three stores → the string trap → the choosing rule → the security line. Complete.
