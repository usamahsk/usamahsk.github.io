Memory & Garbage Collection

Why some objects die and others haunt your app forever.

1 · Readthe concept
2 · Watchthe collector
3 · Practiceget checked
4 · Provesay it out loud
In plain words The garbage collector is an automatic cleaner that frees any object nothing points to anymore. You never free memory by hand in JS — instead, memory leaks happen when you accidentally keep pointing at things you no longer need. A leak isn't "memory isn't freed" — it's "something still holds the arrow."

1.Read the concept

The one rule everything follows

The collector's logic is beautifully simple: an object is garbage the moment it becomes unreachable — no live variable, no property, no closure, no listener holds a path to it. Reachable = kept. Unreachable = freed. You don't control when it frees; you only control whether a path still exists.

let user = { name: "Sam", bigData: new Array(1000000) };
user = null;        // the arrow is gone → the object (and its MB of data)
                    // becomes unreachable → the collector frees it… eventually

The four ways apps accidentally keep arrows

// 1. Forgotten timers
const timer = setInterval(pollServer, 1000);
// ...component is gone, but the timer still holds pollServer — and its closure — forever.
clearInterval(timer);     // the fix. Every timer you start needs a stop.

// 2. Closures over big data
function process() {
  const huge = new Array(1000000).fill("x");
  return () => huge.length;    // this tiny function pins the huge array in memory
}

// 3. Detached DOM nodes
const el = document.querySelector("#modal");
document.body.removeChild(el);   // gone from the screen…
cache.modal = el;                // …but alive in your cache. Detached, retained.

// 4. Ever-growing collections
const logs = [];
function log(msg) { logs.push(msg); }   // grows forever unless you cap or clear it

Notice the pattern: none of these are "memory bugs" in the language — the collector is doing exactly its job. The code kept a path alive. **The fix is always the same discipline: remove what you add** — stop timers, null out caches, prefer WeakMap for metadata that shouldn't pin anything.

WeakMap and WeakSet — the collector's friends

const meta = new WeakMap();
meta.set(domNode, { clicks: 3 });
// if domNode becomes unreachable everywhere else,
// the collector frees BOTH the node and its metadata — automatically.

A WeakMap reference doesn't count as "reachable" — that's its entire purpose. Attaching data to objects whose lifetime you don't control (DOM nodes, library instances) without pinning them. The price: no size, no iteration — you can't inspect what's inside.

Exceptions & traps — the complete list

  • You can't force collection — deleting a property or setting null only *removes a path*; when (or whether) the collector runs is the engine's business.
  • setInterval is the #1 leak — every interval you start needs a matching clearInterval, especially in components that get destroyed.
  • Event listeners leak the same way — a listener on a long-lived object (window, document) holds its closure forever; removeEventListener what you add.
  • Closures pin their whole scope — the tiny callback keeps the big array alive (the closures lesson's trade-off, seen from the memory side).
  • Detached DOM nodes are invisible leaks — off-screen but retained by any variable, cache, or array that mentions them.
  • Maps pin their keys — a Map keyed by objects keeps every key alive. If the keys' lifetime isn't yours to control, that's what WeakMap is for.
  • Console.log can retain objects — logging a large object in devtools can keep it alive during that session; a surprising profiling gotcha.
  • Symptoms vs cause: growing memory, slowing UI, eventual crash = leak somewhere; find it by snapshotting heap before/after the action and looking for objects that should be gone.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "JavaScript frees memory automatically: the collector reclaims any object that's unreachable — no live variable, property, closure, or listener points to it. So leaks aren't the collector failing; they're my code accidentally keeping a reference. The classic four are forgotten intervals and listeners that outlive their component, closures pinning large data, detached DOM nodes held in caches, and ever-growing arrays. The discipline is to remove what you add — clearInterval, removeEventListener, null out caches — and use WeakMap when metadata shouldn't keep its key alive. And to find a leak in practice: snapshot the heap before and after an action and look for what should have died but didn't."

The rule → the four leaks → the discipline → the debugging method. That's the full senior answer.
