CORS & the Browser Sandbox

Why your fetch works in Postman but fails in the browser — the error everyone meets, almost nobody understands.

1 · Readthe concept
2 · Watchthe handshake
3 · Practiceget checked
4 · Provesay it out loud
In plain words The browser has a bodyguard: it refuses to let a page read responses from a different origin (different domain, port, or protocol) unless the server of that response explicitly allows it. CORS is the paperwork for that permission — response headers from the server saying "this origin may read me." It's enforced by the browser only — Postman, curl and servers have no bodyguard, so the same request works there.

1.Read the concept

Same origin — the rule underneath

Two URLs are the same origin only if protocol, domain, AND port all match. http://myapp.com/page reading http://myapp.com/api — fine. Reading https://myapp.com/api (protocol differs), api.myapp.com (domain differs), or myapp.com:3001 (port differs) — all cross-origin, all subject to the bodyguard. The rule exists so that evil.com can't silently read your banking session's data using your logged-in browser.

What actually happens — the surprising part

The browser does send the request. The server does respond — probably with a 200 and your data. And then the browser looks at the response headers: is there an Access-Control-Allow-Origin header permitting your origin? No? Then the browser hides the response from your JavaScript and the fetch throws a CORS error. The data crossed the border; your code just never receives it. That's why the error message says "blocked by CORS policy" while your network tab shows a perfectly good 200.

// the request from https://myapp.com
fetch("https://api.other.com/users");

// the response from api.other.com — WITHOUT permission:
HTTP/1.1 200 OK
Content-Type: application/json
// (no Access-Control-Allow-Origin header)

// → browser: response received, but ORIGIN NOT ALLOWED → fetch throws
// → Postman with the identical request: works perfectly. The bodyguard is browser-only.

The fix is always on the SERVER

// api.other.com must respond with:
Access-Control-Allow-Origin: https://myapp.com    // or * for "anyone" (careful)

// and for requests that "look different" (custom headers, JSON content-type,
// PUT/DELETE methods), the browser first sends an OPTIONS "preflight" —
// which the server must also answer with:
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization

This is the debugging insight that saves hours: CORS is never fixed in the frontend. No amount of fetch options, mode flags, or header tricks in your code will help — the *server* must send the permission headers. If you don't control the server, the fix is a proxy: your own backend fetches the external API (no browser bodyguard there) and forwards it to your page same-origin.

Exceptions & traps — the complete list

  • It works in Postman/curl but fails in the browser — the definitive CORS signature. The bodyguard only exists in browsers.
  • The request SUCCEEDS on the network tab — status 200, data visible there — but JS can't read it. CORS hides the response from JavaScript, it doesn't block the transfer.
  • CORS is fixed on the server (or via your own proxy) — never in frontend code. "Adding headers to my fetch" does nothing.
  • Preflight surprises: a request with Content-Type: application/json or an Authorization header triggers a hidden OPTIONS request first — if the server doesn't answer OPTIONS, the real request never even fires.
  • Origin = protocol + domain + port — all three must match; localhost:3000 and localhost:3001 are different origins (common dev-mode CORS error).
  • * doesn't work with credentials — a request sending cookies requires the server to name your exact origin AND send Access-Control-Allow-Credentials: true; wildcard * is rejected in that mode.
  • Redirects can break CORS — a 302 to another origin without fresh permission headers fails mid-flight.
  • CORS protects READS, not writes — the request often reaches the server anyway (a state-changing POST can execute!); CORS just hides the response. Never rely on CORS as your only access control — that's the server's authentication job.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "CORS is the browser's enforcement of the same-origin policy: a page can only read responses from another origin if that origin's server explicitly allows it via Access-Control-Allow-Origin headers. The subtle part people miss: the request and response both happen — I can see the 200 in the network tab — but the browser hides the body from JavaScript. The signature symptom is 'works in Postman, fails in the browser', because the policy is browser-only. The fix is server-side permission headers — or a backend proxy if I don't control the API — and I know JSON content-types and auth headers trigger a preflight OPTIONS request the server must also handle. And I'd never confuse CORS with authentication: it controls reads, not access."

Policy → the hidden-200 subtlety → the Postman signature → server-side fix → preflight → the security caveat. Complete senior answer.
