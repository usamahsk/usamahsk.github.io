Error Handling

What happens when code fails — and how to catch it without catching everything.

In plain words When something goes wrong, JavaScript throws an object that describes the problem — and that object keeps moving up, function by function, looking for someone who promised to handle it (a catch). If nobody does, the program stops with an error message. So try/catch is simply you raising your hand: "if anything breaks in here, give it to me — I know what to do."

1.Read the concept

The four pieces

try {
  // risky code — monitored from here on
} catch (err) {
  // runs ONLY if something threw above; err is the thrown object
} finally {
  // runs ALWAYS — cleanup belongs here
}

Three facts that answer most interview questions. One: the moment something throws, the rest of the try block is skipped — execution jumps straight to catch. Two: finally runs no matter what — try succeeds, catch handles, even a return inside try can't stop it; that's why it owns cleanup (closing loaders, releasing resources). Three: code after the try/catch runs normally — catching an error means the program survived it.

Throwing — always throw Errors, not strings

throw "oops";                    // works, but: no stack trace, no name
throw new Error("oops");         // right: .message, .stack, instanceof works

class ValidationError extends Error {
  constructor(msg) { super(msg); this.name = "ValidationError"; }
}
try {
  throw new ValidationError("email is invalid");
} catch (err) {
  console.log(err instanceof ValidationError);   // true
  console.log(err.name);                          // "ValidationError"
}

A catch receives whatever was thrown — but the ecosystem (browser, Node, libraries) throws Error objects, and built-ins have types: TypeError (reading property of undefined), ReferenceError (undeclared name), SyntaxError (bad code/JSON), RangeError (bad value range). Custom errors via extends Error let callers instanceof-check and handle differently — that's the senior pattern.

The two boundary rules everyone gets wrong

Rule 1 — catch is not a time machine. A try/catch protects the code inside it, synchronously. A callback that throws later (inside setTimeout) escapes that try entirely — the stack has already unwound:

try {
  setTimeout(() => { throw new Error("too late"); }, 100);   // escapes!
} catch (err) { /* never runs */ }

Rule 2 — async needs async catch. A rejected promise is not a thrown exception; it's a rejection travelling through the promise chain. So promise-style code catches with .catch() — and await bridges the two worlds: a rejection at an await point becomes a throwable, caught by an ordinary try/catch:

// promise style
fetchData().catch(err => console.error(err));

// async/await style — the SAME failure, caught sync-style
try {
  const data = await fetchData();
} catch (err) {
  console.error(err);
}
And the anti-pattern An empty catch (err) {} that swallows everything makes failures invisible and debugging impossible. Either handle the error meaningfully, add context and rethrow it, or let it propagate. "Never catch what you can't handle" — a sentence worth saying in interviews.

Exceptions & traps — the complete list

  • try/catch is synchronous only — a throw inside a setTimeout callback escapes the try entirely (the stack has already unwound).
  • finally always runs — even over a return in try; cleanup lives there because nothing can prevent it.
  • catch recovers: after catching, the program continues — the error is handled, not fatal.
  • throw "string" loses the stack — always throw new Error(msg) or a custom subclass so callers get instanceof and stack traces.
  • Empty catch hides failures — handle meaningfully, add context and rethrow, or let it propagate. "Never catch what you can't handle."
  • Awaited rejections throw: try { await fetch() } catch works — but the same fetch without await needs .catch.
  • Know the built-in types: TypeError (property of undefined), ReferenceError (undeclared name), SyntaxError (bad code/JSON), RangeError (bad value range).
  • JSON.parse throws on bad input — always wrap it; "Unexpected token" crashes are everywhere.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "A thrown error unwinds the call stack until the nearest catch — the rest of the try block is skipped, catch receives the thrown object, and finally runs no matter what, even over a return, which is why cleanup lives there. I throw Error objects — or custom subclasses — never strings, so callers get stack traces and can instanceof-check. Two boundaries matter: try/catch is synchronous, so a throw inside a setTimeout callback escapes it, and a rejected promise is caught with .catch — unless I'm using await, which turns rejections into ordinary throwables I can catch with try/catch. And I never leave an empty catch: handle it, wrap it with context, or let it propagate."

Mechanism → finally → custom errors → the two boundary rules → the anti-pattern. That's the full senior answer.
