Variables: let & const

Two keywords, one rule of thumb — and the const trap that catches everyone once.

In plain words A variable is a name-tag tied to a value. let lets you re-tie the tag to a different value later; const says "this tag stays on this value forever." But careful — the rule is about the tag, not the value: a const list can still have items pushed into it. The tag is locked, not the box.

1.Read the concept

Step 1 — what a variable really is

Forget the keywords for a second. A variable is just a name-tag tied to a value:

let score = 10;

score is the tag. 10 is the value. That's all three keywords do — they create the tag. The difference between them is what rules the tag has to live by. Keep this picture; everything below hangs on it.

Step 2 — rule one: can you re-tie the tag?

let score = 10;
score = 25;        // ✅ fine — re-tied to a new value

const MAX = 5;
MAX = 6;           // 💥 TypeError: Assignment to constant variable

let says: "this tag can be re-tied later if needed." const says: "this tag stays on this value forever."

Stop — here is the famous const trap. Think about it before reading on:

const list = [];
list.push(1);      // ✅ works fine!
list.push(2);      // ✅ still fine!
list = [];         // 💥 TypeError — THIS is what const forbids

Why does pushing work when reassigning fails? Because const locks the tag, not the box. The arrow from the name to the array never moves — but the array's contents can change all day. Pushing doesn't re-tie the tag; it changes what's inside the box the tag points at.

Step 3 — the sentence worth memorizing "const locks the arrow, not the box." A locked name can still point at living, changing things. (If you truly need an unchangeable object, that's Object.freeze() — a different tool for a different job.)

Step 4 — rule two: where the tag lives

Tags have a neighborhood — the places where the name is visible. This is where var and let/const behave completely differently:

function test() {
  if (true) {
    var v = 1;     // var ignores the block — it lives in the FUNCTION
    let l = 2;     // let respects the block — it lives inside these { }
  }
  console.log(v);  // 1        ← leaked out of the if-block!
  console.log(l);  // 💥 ReferenceError — l died with its block
}
  • var is function-scoped — it pretends { } blocks (if, for, while) don't exist; only a function boundary contains it.
  • let and const are block-scoped — they live and die inside their nearest { }.

This is not trivia — it's the bug that let was invented to fix:

for (var i = 0; i < 3; i++) { }
console.log(i);    // 3 — i leaked out of the loop!

for (let j = 0; j < 3; j++) { }
console.log(j);    // 💥 ReferenceError — j is gone, as it should be

Step 5 — rule three: the "exists early" weirdness

Before any code runs, JavaScript takes one quick look through it and registers every name (that's hoisting — full model in the Scope lesson). What you get when you touch a name too early depends on the keyword:

console.log(x);   // undefined — var: registered early with "no value yet"
var x = 5;

console.log(y);   // 💥 ReferenceError — let: registered but LOCKED
let y = 10;       //   until its own line runs. That window = temporal dead zone

Both are registered early — but var shows up holding undefined, while let/const show up locked behind a door until their line executes. Function declarations are the friendliest of all: the whole function is available from line 1.

The policy, in one line const by default, let when it must change, var never in new code. Every const is a promise the reader can trust — accidental reassignment becomes impossible, and the linter enforces it for free. You reach for let only when a variable genuinely changes (loop counters, running totals). var has no role in new code — but you must read it fluently: old codebases are full of it, and its loop-leaking, undefined-hoisting behavior is exactly what interviewers probe.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "let and const are block-scoped and live in the temporal dead zone until their declaration line runs. const locks the binding, not the value — you can't reassign the name, but you can still mutate the contents of a const array or object, which is why pushing to a const array works. My policy is const by default, let when the variable genuinely gets reassigned, and var only when reading legacy code, where it's function-scoped and hoisted as undefined."
