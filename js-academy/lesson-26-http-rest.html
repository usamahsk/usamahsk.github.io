HTTP & REST

The language your fetch speaks — verbs, status codes, and the vocabulary of every API discussion.

2 · Watchthe anatomy
3 · Practiceget checked

In plain words Every API call is a letter with two halves: your request (where, what you want done, optional payload) and the server's response (a status number saying how it went, plus the data). HTTP is the format of the letter; REST is a convention for what the verbs and addresses should mean.

1.Read the concept

The verb is the intent

GET    /users        → "read the list"        (never changes anything)
GET    /users/7      → "read user 7"
POST   /users        → "create a new user"    (body carries the data)
PUT    /users/7      → "replace user 7 entirely"
PATCH  /users/7      → "update parts of user 7"
DELETE /users/7      → "delete user 7"

REST's contribution is the convention: URLs name things (nouns), methods express actions (verbs). /users/7 is a resource; what you do to it is the method. Two properties come with the verbs: GET is safe (no side effects) and GET, PUT, DELETE are idempotent — repeating them gives the same result as doing it once (deleting twice = still deleted). POST is neither — that's why double-clicking "Pay" needs client-side protection (the throttle lesson!).

The response: a number that starts the story

200 OK — here's your data
201 Created — your POST made something
204 No Content — done, nothing to return (DELETE)
400 Bad Request — your input is malformed
401 Unauthorized — who are you? (log in)
403 Forbidden — I know you; you may not
404 Not Found — no such resource
429 Too Many Requests — slow down
500 Server Error — the server's own crash

The first digit is the family: 2xx success, 3xx redirect, 4xx your mistake, 5xx the server's mistake. The interview's favorite pair is 401 vs 403: 401 = "I don't know who you are" (missing/invalid credentials), 403 = "I know exactly who you are, and the answer is no." And a sharp junior trap: a failed login should be 401 (or 400), never 404 — hiding behind "not found" is an anti-pattern.

Where data lives in a request

fetch("/users?role=admin&page=2", {          // QUERY params: filtering/sorting
  method: "POST",
  headers: { "Content-Type": "application/json",   // what I'm sending
             "Authorization": "Bearer " },  // who I am
  body: JSON.stringify({ name: "Sam", age: 30 })   // the payload itself
});

// the response
res.status;      // 201
await res.json(); // { id: 7, name: "Sam", age: 30 }

Three places data can live, each with a job: query params shape what you're asking for (pagination, filters), headers carry metadata (identity, content type), body carries the payload itself (only POST/PUT/PATCH have one). And one more trap from earlier lessons applies: fetch resolves even on 404 and 500 — res.ok must be checked, or errors sail through as if they were data.

Exceptions & traps — the complete list

  • fetch doesn't throw on HTTP errors — only network failures. Check res.ok (or status) or a 500 arrives as "valid" data.
  • 401 vs 403: unauthenticated vs unauthorized — knowing which failed tells you whether to log in again or fix permissions.
  • GET requests have no body — filters go in query params; trying to put a body on GET confuses servers and proxies.
  • POST is not idempotent — double-submit creates two records; guard the button (disable while pending) or the server dedupes.
  • PUT vs PATCH: PUT replaces the whole resource (missing fields reset!); PATCH updates only what you send. Sending PATCH-style data via PUT wipes fields.
  • Content-Type must match the body — JSON body without Content-Type: application/json arrives as text on many servers; the header is part of the message.
  • Status codes are the server's opinion — real APIs violate conventions (200 with an error body!). Read the code AND the body; design your own APIs to keep the promise.
  • CORS interacts here — auth headers and JSON content-types trigger preflights (the CORS lesson), so "it worked without the header" is a common mystery solved.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "HTTP is the request-response format; REST is the convention on top — nouns in the URLs, verbs expressing intent: GET reads safely, POST creates, PUT replaces, PATCH updates partially, DELETE removes. Status codes come in families — 2xx success, 4xx my mistake, 5xx the server's — and the pair I always get right is 401 unauthenticated versus 403 unauthorized. Data travels in three places: query params shape the ask, headers carry identity and content type, the body carries the payload. And I know fetch resolves even on 500s, so I check res.ok before trusting the data."

Verbs → codes → data locations → the fetch trap. The working developer's complete answer.
