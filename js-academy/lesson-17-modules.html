Modules

How JavaScript splits one program into many files — without everything leaking into everything else.

1 · Readthe concept
2 · Watchthe connection
3 · Practiceget checked
4 · Provesay it out loud
In plain words A module is a file that is its own private room. Nothing inside it is visible to other files — unless the file deliberately hands something out with export, and another file picks it up with import. Before modules, every script shared one giant global room, and any file could stomp on any other file's variables.

1.Read the concept

The problem modules solve

Imagine three script tags on one page. Each declares let count = 0 for its own feature. In old-style scripts, they'd collide — the third one silently overwrites the first two, because everything lives in the same global room. Modules end this: every file is its own scope, and sharing happens only through explicit doors.

Exporting — the doors out

// math.js
export const PI = 3.14159;              // named export — can be many
export function double(n) { return n * 2; }

export default function sum(a, b) {     // default export — exactly ONE per file
  return a + b;
}

Importing — the doors in

// app.js
import sum from "./math.js";              // default: ANY name you choose
import { PI, double } from "./math.js";   // named: the EXACT names, in braces
import * as math from "./math.js";        // everything, namespaced

sum(2, 3);        // 5
double(4);        // 8
math.PI;          // 3.14159

The asymmetry is the interview question: default imports get any name you like (there's only one, so the name is your choice); named imports must match the exported names exactly — braces, correct spelling. Get a name wrong and you don't get an error at import time — you get undefined at use time, which is far sneakier.

ESM vs CommonJS — the two worlds

// ES Modules (ESM) — the browser standard, modern Node
import fs from "fs";
export default sum;

// CommonJS — older Node, still everywhere in real codebases
const fs = require("fs");
module.exports = sum;

Same idea, two dialects. ESM loads asynchronously, works natively in browsers, and supports tree-shaking (bundlers drop unused exports). CommonJS loads synchronously and was Node's original system. Reading old code means reading require; writing new code means import.

Exceptions & traps — the complete list

  • Wrong named import = undefined, not an error — import { dubbel } doesn't crash the import; it surfaces later as "undefined is not a function". Check spelling first.
  • One default per file — a second export default is a SyntaxError. Named exports: unlimited.
  • Imports are hoisted — all imports resolve before any of your code runs; you can't "conditionally import" with an if (that needs dynamic import()).
  • Exports are LIVE bindings, not copies — if the module later changes an exported let, importers see the new value. (Const exports never change.)
  • Circular imports (A imports B imports A) don't crash but can hand you undefined depending on what's accessed first — a design smell worth refactoring away.
  • Module code runs once — importing the same module from ten files executes it a single time; its exports are shared by everyone.
  • The extension matters in the browser — import "./math.js" needs the full path in browsers; bundlers and Node are more forgiving.
  • Top-level await works in modules only — another reason modules changed the language.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "A module is a file with its own private scope — nothing leaks to other files unless it's exported. There's one default export per file, which the importer can name anything, and unlimited named exports, which must be imported by their exact names in braces — get a name wrong and you get undefined at use time, not an error. ES Modules are the standard: they hoist imports, run module code exactly once, and exports are live bindings. CommonJS is the older Node dialect — require and module.exports — which I read fluently but don't write in new code."
