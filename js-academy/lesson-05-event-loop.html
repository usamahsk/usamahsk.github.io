The Event Loop

Why JavaScript does one thing at a time — and still handles timers, clicks, and network requests "at once".

In plain words JavaScript can only do one thing at a time — there's a single to-do list it works through, top to bottom. So who handles timers, clicks and downloads? The browser does that work outside the list. The event loop is the helper that keeps checking: "list empty? okay — first everything from promises, then one timer, then look again." Same check, forever.

1.Read the concept

The uncomfortable fact: JavaScript is single-threaded

JavaScript has one call stack. A function is called, it goes on the stack; it returns, it comes off. Only the top frame ever runs. Take this seriously and the consequences are brutal:

while (true) { }        // the stack never empties
console.log("never printed");

But wait — you know the browser does many things "simultaneously": timers fire, requests complete, buttons react. If JS can only run one thing at a time, who is doing all that?

The browser is. Timers, network requests, and DOM events are not JavaScript — they're facilities the browser provides (Web APIs; in Node, the equivalent runtime facilities). Your code hands work to them and moves on immediately. They run in parallel with your code, outside the JS thread. This division of labor is the entire trick.

Five pieces, one rule

  • Call stack — where your synchronous code runs. One frame at a time.
  • Web APIs — the browser's parallel zone: timers counting down, requests in flight, listeners waiting.
  • Microtask queue — where promise callbacks wait (.then, await continuations).
  • Macrotask queue — where timer and event callbacks wait.
  • Event loop — the controller that applies the rule below.
The rule — memorize it as one sentence When the call stack is empty: drain ALL microtasks, then take ONE macrotask, then repeat. Microtasks spawned during the drain still run in the same drain — the microtask phase can't be interrupted by timers.

Walk the classic example by hand

console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");

output: 1, 4, 3, 2

Narrate it — this narration is the interview answer in motion:

  • "1" — synchronous, runs on the stack.
  • setTimeout(...) — the callback is not run. It's handed to the browser's timer, and even with delay 0 it goes to the macrotask queue. JS moves to the next line instantly.
  • .then(...) — the promise is already resolved, so its callback goes to the microtask queue. Still not run — the stack is busy.
  • "4" — synchronous. Now the stack is empty.
  • The event loop drains microtasks first → "3". Then takes one macrotask → "2".
The two sentences interviewers are listening for 1. setTimeout(fn, 0) does not mean "run in 0 ms" — it means "queue this; it runs at the earliest moment the stack is free." If the stack stays busy for 5 seconds, it runs after 5 seconds. The delay is a minimum, never a guarantee.
2. Microtasks always jump ahead of macrotasks — promise callbacks run before timer callbacks, even if the timer expired first.

How this connects to async/await

await is not magic — it's this exact machinery. When a function hits await, everything below that line is scheduled as a microtask:

async function go() {
  console.log("start");
  await Promise.resolve(5);   // ← the pause point
  console.log("end");         // queued as a microtask
}
go();
console.log("after");

output: start, after, end

Read it carefully: "start" prints before "after", because an async function runs synchronously up to its first await. Calling go() executes it like any function — the pause happens only at the await line. So the sharp interview answer to "is async code synchronous?" is: both — everything before the first await runs synchronously; everything after it is a microtask.

Exceptions & traps — the complete list

  • setTimeout(fn, 0) is a MINIMUM, never a guarantee — the callback waits for the stack + all microtasks, however long that takes.
  • A blocked stack delays everything — one 3-second loop delays timers, clicks, and page rendering.
  • Microtasks spawned during the drain run in the same drain — a .then queueing a .then still finishes before any timer.
  • Async functions run synchronously until the first await — f() executes its opening lines immediately; only what's below the await is deferred.
  • The promise executor is synchronous — code inside new Promise(fn) runs before the next line, not in a microtask.
  • setInterval doesn't wait for your async work — if the callback takes longer than the interval, runs overlap. Prefer chained setTimeout for repeating async tasks.
  • Rendering happens between tasks — that's why long tasks make the page visually stuck even when JS is "working fine".

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "JavaScript runs on a single call stack. Slow work — timers, network, events — is handed to browser APIs, which run in parallel; when each finishes, its callback is queued: promise callbacks in the microtask queue, timers and events in the macrotask queue. The event loop runs the current code until the stack is empty, then drains all microtasks — including any new ones spawned during the drain — then takes exactly one macrotask, and repeats. That's why setTimeout(fn, 0) doesn't mean 0 milliseconds — the delay is a minimum, and the callback waits for the stack and every microtask — and why promise callbacks always beat timer callbacks."

Structure: single thread → browser APIs → two queues → the cycle rule → the two proofs. If a follow-up comes ("what about a busy loop?"), you're ready: a blocked stack blocks everything, including rendering.
