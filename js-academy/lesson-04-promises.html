Promises & async/await

Placeholder objects for values that don't exist yet — and the syntax that makes them readable.

1 · Readthe concept
2 · Watchthe state machine
3 · Practiceget checked

In plain words A promise is a receipt for something that isn't ready yet — like the slip you get after ordering food. It starts as pending ("still cooking"), then becomes either fulfilled ("here's your order") or rejected ("sorry, it failed") — and once it lands on one of those, it stays there forever.

1.Read the concept

The problem it solves

Your code runs line by line, but the real world doesn't: network requests, timers, file reads all take time. The old solution was callbacks — "call this function when you're done":

getUser(1, function (user) {
  getPosts(user.id, function (posts) {
    getComments(posts[0].id, function (comments) {
      // …and every step needs its own error check, repeated
    });
  });
});

Each step nests inside the previous one — "callback hell" — and a failure at step 3 needs error handling written at every level. A promise inverts this: instead of handing functions forward, the async operation hands you back a receipt immediately. The receipt is the promise. It says: "the value isn't here yet, but this object will hold it the moment it arrives."

Three states, one-way

A promise is always in exactly one of three states:

  • pending — the work is still running; the value doesn't exist yet.
  • fulfilled — success. The promise now holds the value; every queued .then will run.
  • rejected — failure. The promise now holds the error; every queued .catch will run.

Fulfilled and rejected are together called settled — and settling is final. A promise that fulfilled can never reject, and vice versa. That one-way guarantee is what makes promises trustworthy in a way raw callbacks never were: consumers can rely on the final state.

The chain — and the one rule that makes it work

getUser(1)
  .then(user => getPosts(user.id))   // return a promise → chain waits
  .then(posts => render(posts))      // return anything → next .then gets it
  .catch(err => showError(err));     // safety net for EVERYTHING above

One mechanical fact powers all of it: every .then() returns a new promise. Whatever you return inside a handler becomes the input of the next handler — and if you return another promise, the chain pauses and waits for it to settle first. That's how sequencing works without nesting: the chain flattens callback hell into a readable top-to-bottom list.

Errors work like unwinding exceptions: a rejection skips every .then between it and the nearest .catch — exactly like an exception jumping to the nearest try block. One catch at the bottom protects the whole sequence.

async/await — the same machine, better clothes

async function load() {
  try {
    const user  = await getUser(1);          // pauses THIS function…
    const posts = await getPosts(user.id);   // …not the whole program
    render(posts);
  } catch (err) {
    showError(err);                          // rejected promise lands here
  }
}

Three facts, and each one is a common interview question:

  • An async function always returns a promise — return 5 secretly returns Promise.resolve(5).
  • await pauses only the current function and schedules its remainder as a microtask — the rest of the program keeps running (event loop lesson).
  • A rejected promise throws at the await point, so ordinary try/catch works.

The trap that separates seniors: sequential vs parallel

// SLOW — 2 seconds: fetchB doesn't even START until fetchA finishes
const a = await fetchA();
const b = await fetchB();

// FAST — 1 second: both start immediately; await just collects results
const [ra, rb] = await Promise.all([fetchA(), fetchB()]);

The insight in one line: await doesn't start anything — it waits for something already running. Start all independent requests first, then await them together. Know the four combinators: Promise.all (fails fast), allSettled (never fails — gives every outcome), race (first to settle, success or failure), any (first success).

Exceptions & traps — the complete list

  • Settling is final — a fulfilled promise can never reject (and vice versa). Consumers can trust the outcome.
  • The executor runs synchronously — new Promise(fn) calls fn immediately; only resolve/reject consequences are async.
  • Forgetting to return inside .then silently feeds undefined to the next handler — the #1 chain bug.
  • catch RECOVERS: after a catch, the chain continues as fulfilled — later .then handlers run.
  • Sequential await is slow: await a; await b; runs b only after a finishes — start both, then Promise.all.
  • await doesn't start work — it waits for it. The sentence that separates seniors from everyone else.
  • Promise.all fails fast: one rejection rejects everything. Need every outcome? allSettled.
  • An async function ALWAYS returns a promise — return 5 is Promise.resolve(5).
  • Unhandled rejections — a rejected promise with no catch crashes the console; always end chains with a catch.
  • await only works inside async functions (or top-level in modules) — elsewhere it's a syntax error.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "A promise is a placeholder for a future value with three one-way states — pending, fulfilled, rejected — and once settled it never changes. Every .then returns a new promise, which is why chains work, and a rejection skips ahead to the nearest .catch like an unwinding exception. async/await is syntax over the same machinery: an async function always returns a promise, await pauses only the current function until the promise settles, and rejections throw into try/catch. For independent requests I start them together and await Promise.all — because await doesn't start work, it waits for it."

That last sentence is the one interviewers remember. It proves you understand the machinery, not the syntax.
