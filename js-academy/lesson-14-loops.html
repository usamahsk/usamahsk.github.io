Loops

Doing it a hundred times without writing it a hundred times.

In plain words A loop repeats work while a condition says "keep going". Every loop is the same three moves: set up → check → do the work → take one step closer to stopping. Forget that last step and you meet the most famous bug in programming: the loop that never stops.

1.Read the concept

A loop repeats work. Every loop is the same three moves:

for (let i = 0; i < 3; i++) {
  console.log(i);
}
//     │      │     └─ 3rd move: step closer to stopping (runs AFTER each pass)
//     │      └─ 2nd move: check — false means stop
//     └─ 1st move: setup — runs ONCE before everything

Set up → check → work → step toward stopping. Hold that rhythm; every surprise below comes from when each move happens.

Surprise #1 — the check comes first

let n = 5;
while (n < 3) {
  console.log("runs");     // never executes...
  n++;
}
console.log("after");       // "after" — the loop ran ZERO times

A loop whose condition starts false does nothing at all. while can run zero times — and do…while exists precisely to guarantee at least one pass (body first, check after).

Surprise #2 — forget the step, freeze the page

let m = 0;
while (m < 3) {
  console.log(m);          // 0, 0, 0, 0… forever — and the PAGE IS FROZEN
}

No step toward stopping → the condition is true forever → the call stack never empties → the event loop can never take another task. No clicks, no timers, no rendering. One missing m++ takes down the whole page.

Now the definition makes sense A loop repeats while the condition says "keep going" — and can only stop if something moves it toward stopping. Check first, work second, step last.

of vs in — the twins that are opposites

const arr = ["a", "b"];
for (const item of arr) console.log(item);   // "a", "b"   ← VALUES
for (const k in arr) console.log(k);         // "0", "1"   ← KEYS, as STRINGS!

for (const key in { name: "Sam" }) console.log(key);  // "name" — objects: yes

of walks an iterable's values — arrays, strings, Maps. in walks an object's keys — and on an array those keys are the strings "0", "1" (array keys are strings — arrays are objects, remember), plus any inherited extras. Arrays get of or the array methods; in belongs to objects.

Exceptions & traps — the complete list

  • Zero runs: while and for check before the body — they can run zero times. Only do…while guarantees one pass.
  • Infinite loop: a missing update freezes the entire page — clicks included (that's the event loop lesson in action).
  • for…in on arrays gives string indices and inherited keys — use for…of or the array methods instead.
  • for…of fails on plain objects — {} is not iterable. Use Object.entries(obj): for (const [k, v] of Object.entries(o)).
  • continue vs break: continue skips only this pass (jumps straight to the update); break exits the loop entirely.
  • Off-by-one: i <= arr.length reads one position too far (undefined) — the idiom is i < arr.length.
  • Removing items while looping forward skips the element after each removal — loop backwards, or build a filtered copy instead.
  • let in the loop head creates a fresh binding per iteration — that's exactly why the setTimeout loop prints 0, 1, 2 with let and 3, 3, 3 with var (the closures lesson, live).

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "Every loop has three parts: a start state, a condition checked before each pass, and a step toward stopping. for is the general form; while checks before the body so it can run zero times, do…while runs at least once; and for iterating collections I use for…of — which gives VALUES — reserving for…in for object keys, since on arrays it yields string indices plus inherited keys. I control loops with continue to skip a pass and break to exit, and I know an infinite loop — a forgotten update — freezes the whole page because the call stack never empties."

The last sentence quietly connects to the event loop — that's what interviewers remember.
