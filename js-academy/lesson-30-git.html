Git Beyond the Basics

You know add, commit, push — this is the rest of the vocabulary you'll use every working day.

In plain words Git is a time machine with a safety spectrum: some commands only move labels (safe), some rewrite history (dangerous). Every panic moment in Git is choosing the right tool for how much you're willing to lose — and this lesson draws that map.

1.Read the concept

The daily flow, upgraded from "just committing"

git status                 # ALWAYS first — what changed, what's staged?
git diff                   # review your own changes before committing
git add -p                 # stage in HUNKS — choose pieces, don't blanket-add
git commit -m "Add todo deletion with event delegation"   # message = WHY

The upgrade from beginner to professional isn't new commands — it's reviewing before saving. git status and git diff before every commit is the habit; add -p is the power move: it walks through your changes chunk by chunk and lets you commit related pieces separately instead of one " assorted fixes" blob.

stash — the "let me try something" tool

# you're mid-feature, but an urgent bug needs fixing NOW
git stash                  # park your half-done changes safely away
git checkout main          # switch cleanly — working directory is clean
# ...fix the bug, commit, push...
git checkout feature
git stash pop              # your half-done work returns, exactly as it was

stash takes uncommitted changes and stores them on a shelf; stash pop takes them back. Without it you'd either commit garbage ("WIP") or lose work. git stash list shows the shelf — you can stack multiple stashes.

Undo — the safety map (the heart of this lesson)

git restore file.js        # discard UNCOMMITTED changes to one file — gone forever
git restore --staged f.js  # unstage: keep the changes, just take them off the stage

git reset --soft HEAD~1    # undo the LAST COMMIT, keep the changes staged
git reset --hard HEAD~1    # undo the last commit and DESTROY the changes — careful

git revert           # NEW commit that reverses an old one — SAFE on pushed code
The interview question: revert vs reset revert writes a new commit that undoes an old one — history is preserved, teammates get the fix, pushed code stays safe. reset moves the branch pointer and can erase history — fine for your own unpushed mistakes, dangerous on shared branches. One-liner: "revert for shared history, reset for local cleanup."

Branches — where real work happens

git switch -c feature/filter    # create + move to a new branch
# ...work, commit...
git switch main
git merge feature/filter        # bring the work in
git branch -d feature/filter    # clean up the merged branch

A branch is a movable label on a line of commits — creating one costs nothing. The professional rhythm: main stays shippable; every feature/fix gets its own branch; merge when it works. (checkout still works for switching — switch is its modern, less error-prone replacement.)

Exceptions & traps — the complete list

  • reset --hard destroys uncommitted work permanently — no stash, no trash can. Run git status before any hard command.
  • reset on pushed code rewrites shared history — teammates' pulls break; that's what revert is for.
  • git checkout is overloaded (switch branches AND discard files) — the reason git switch and git restore were invented: one command, one job.
  • stash doesn't include untracked files by default — new files need git stash -u.
  • A bad commit message is commit-amend territory: git commit --amend -m "better" — but only BEFORE pushing; amending pushed commits rewrites history.
  • Detached HEAD: checking out a commit hash instead of a branch leaves you "on no branch" — commits there can be lost on checkout; create a branch first if you want them.
  • Merge conflicts aren't errors — Git paused mid-merge and marked the choices (<<<<<<< ======= >>>>>>>) in the files; you edit, resolve, add, and commit. Abort with git merge --abort if lost.
  • git push --force is the nuclear option — it overwrites remote history; use --force-with-lease at minimum, and never on shared branches.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "Git is a time machine with a safety spectrum. My daily flow is status, diff, add -p to stage in hunks, commit with a message that explains why. For half-done work I stash and pop; for undoing, I pick by safety: restore discards uncommitted changes, reset --soft rewinds the last commit keeping the work, reset --hard destroys it, and revert creates a new commit reversing an old one — which is what I use on anything already pushed, because reset rewrites shared history. I work on feature branches and merge to main when green. The one-liner: revert for shared history, reset for local cleanup."

The spectrum → the daily flow → stash → the revert/reset one-liner → branches. That's a confident professional answer.
