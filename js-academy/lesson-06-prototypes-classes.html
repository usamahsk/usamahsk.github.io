Prototypes & Classes

JavaScript has no classes under the hood — it has objects linked to other objects.

2 · Watchthe animation
3 · Practiceget checked

In plain words Objects in JavaScript don't hold copies of shared behavior — they hold a link to another object that has it. When you ask for something that isn't there, JavaScript follows that link, then the next one, until it finds it — or runs out of links. Everything else in this lesson is just that one idea wearing different syntax.

1.Read the concept

Objects don't copy — they link

In most class-based languages, inheritance copies behavior from a blueprint into each instance. JavaScript does something cheaper and more flexible: every object holds a hidden link to another object (its prototype), and property lookup follows those links. Nothing is duplicated — one shared method serves a thousand objects:

const animal = {
  eats: true,
  walk() { console.log("walking"); }
};

const rabbit = Object.create(animal);   // rabbit's prototype IS animal
rabbit.name = "Bunny";                  // an OWN property

rabbit.name;    // "Bunny"  — found immediately, no walk needed
rabbit.eats;    // true     — NOT on rabbit… found on animal via the chain
rabbit.fly;     // undefined — found nowhere; the walk ended at null

Three reads, three different outcomes: an own property, an inherited one, and a miss. Notice the miss returns undefined — not an error. That silence is a classic source of bugs and a classic interview question.

Where new and class fit in

Remember the four steps of new from the this lesson? Step 2 — "link its prototype" — is this whole lesson in miniature. Every function automatically gets a .prototype object, and new links the fresh object to it:

function Person(name) {
  this.name = name;               // own property, per instance
}
Person.prototype.sayHi = function () {   // ONE shared function
  console.log("Hi, I'm " + this.name);
};

const p = new Person("Sam");
p.sayHi();     // works — sayHi lives on Person.prototype, found via the chain
p.__proto__ === Person.prototype;   // true — the link, made by new

The class keyword (ES2015) generates exactly this shape — constructor + methods on .prototype — with cleaner syntax and some extras like super:

class Person {
  constructor(name) { this.name = name; }   // runs on new → own property
  sayHi() { console.log("Hi, I'm " + this.name); }  // lives on Person.prototype
}
The sentence that wins the interview "The class keyword is syntax over the prototype chain — JavaScript implements inheritance with linked objects, not copied blueprints." Say that, then prove it: methods defined in a class are shared through the prototype (which is why putting methods inside constructor — one copy per instance — is wasteful).

Own vs inherited — and the one tool to tell them apart

p.hasOwnProperty("name");    // true  — set by the constructor
p.hasOwnProperty("sayHi");   // false — inherited from the prototype

This distinction matters in real code: for…in walks inherited properties too, while Object.keys() lists only own ones — a subtle bug factory, and therefore a favorite quiz question.

Exceptions & traps — the complete list

  • Methods live on the prototype, not the instance — declaring them inside constructor creates one copy per instance: wasted memory, inconsistent with class expectations.
  • Constructor returning an object overrides new's result — return { custom: 1 } replaces the freshly built this; returning a primitive is ignored.
  • for…in walks the chain; Object.keys doesn't — inherited keys leak into for…in loops.
  • Modifying a shared prototype affects every instance — Person.prototype.sayHi = … changes all Persons, even ones already created (feature and footgun).
  • __proto__ vs .prototype: __proto__ is the instance's link; .prototype is the blueprint functions carry for new to link to. Two different things with confusingly similar names.
  • Missing property = undefined, silently — a typo like user.nmae doesn't error; it hands you undefined and the crash happens lines later.
  • Object.create(null) has NO inherited methods — not even hasOwnProperty; it's a truly bare object.
  • Overwriting via the chain: setting rabbit.eats = false creates an OWN property that shadows the inherited one — the prototype keeps its value.

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "JavaScript implements inheritance with the prototype chain, not with copied classes. Every object links to a prototype object; when you read a property, the engine checks the object itself, then walks up the links until it finds the property or reaches null — a miss returns undefined. Methods live on the constructor's .prototype so one shared function serves all instances; that's exactly what the class keyword generates — it's syntax over the prototype chain. And own versus inherited properties are distinguishable with hasOwnProperty, which matters because for…in walks inherited keys while Object.keys doesn't."

Structure: mechanism → lookup rule → where methods live → the class sentence → the practical footnote. Full marks in one breath.
