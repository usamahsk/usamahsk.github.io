Closures

The concept most developers use every day and still can't explain in an interview.

Where we're heading By the end of this page you'll hold the sentence most developers get wrong: what a closure actually is, beyond "a function inside a function". We build it in five steps — from a fact you already know to the interview answer.

1.Read the concept

Step 1 — the fact closures are built on

Functions can read variables declared outside themselves. Nothing surprising yet:

let count = 0;            // global variable

function increment() {
  count++;                // the function reaches OUT and changes it
}

increment();
increment();
console.log(count);       // 2

output: 2

Keep this example in your head — closures are built on exactly this one fact, nothing more.

Step 2 — now the twist

Move that variable inside another function, and return the inner function out of it. Read slowly, and actually run it in your head:

function makeCounter() {
  let count = 0;          // local to makeCounter

  return function () {    // born INSIDE makeCounter's scope
    count++;
    return count;
  };
}

const counter = makeCounter();  // makeCounter runs… and FINISHES here
counter();  // 1
counter();  // 2
counter();  // 3

output: 1, 2, 3

Stop. Think about why this should be impossible. makeCounter() finished executing on the middle line. Its count was a local variable — and in most languages, when a function ends, its local variables are thrown away. But here, three calls later, count is not only still alive — it has remembered every increment, changing between calls. The returned function didn't just escape. It took its birthplace with it.

Step 3 — now the definition makes sense A closure is a function bundled with a permanent link to the scope where it was born. The outer function's execution is over; the link keeps its variables alive — and private — for as long as the function exists.
The trap most people fall into Saying "a closure is a function inside a function." That describes the syntax — plenty of nested functions are not closures. The essence is the remembered variables: function + captured scope. An interviewer hears the difference between those two answers instantly — and it's often the whole decision.

Step 4 — the detail that proves understanding

Every call to makeCounter() runs the body again, creating a fresh scope with a fresh count. Two counters never share state:

const a = makeCounter();
const b = makeCounter();

a(); a(); a();      // 1, 2, 3  — a's own count
b();                // 1        — b's count is untouched

If you can explain why b() returns 1 and not 4 — two calls of makeCounter() built two separate scopes, and each returned function remembers its own — you understand closures better than most candidates. This exact question separates memorization from understanding.

Step 5 — you've been writing closures for six years

Under other names. Every callback that reaches out to a variable from its surroundings is one — which is why this topic dominates interviews: it cleanly separates "I write code" from "I know what the code does."

// 1. Private state — the variable is unreachable from outside
function wallet(start) {
  let cash = start;
  return {
    deposit(n)  { cash += n; return cash; },
    balance()   { return cash; },
  };
}
const w = wallet(100);
w.deposit(50);          // 150
w.cash = 999999;        // adds a useless property on the object —
console.log(w.balance()); // 150 — cash itself is untouchable
// 2. Functions that remember a setting
function multiplier(factor) {
  return n => n * factor;    // remembers `factor` forever
}
const double = multiplier(2);
const triple = multiplier(3);
double(5);                   // 10
triple(5);                   // 15
// 3. State between calls — the debounce from every search box
function debounce(fn, wait) {
  let timer;                          // remembered BETWEEN calls
  return function (...args) {
    clearTimeout(timer);              // cancel the previous attempt
    timer = setTimeout(() => fn(...args), wait);
  };
}
The cost — worth mentioning in interviews A closure's captured variables cannot be garbage-collected while the function lives. Ten thousand closures over a big object is ten thousand retained copies. That trade-off — privacy and memory of state, paid for in memory — is the senior-level nuance.

Exceptions & traps — the complete list

  • The loop trap: for (var i…) + setTimeout prints 3, 3, 3 — one shared var. Fixes: let (fresh binding per iteration) or an IIFE copying i into a parameter.
  • Closures capture variables, not values — the callback sees the variable's value at call time, not at creation time.
  • Separate calls = separate scopes: two makeCounter() calls give two independent counts — they never share state.
  • Memory cost: captured variables can't be garbage-collected while the closure lives — a closure over a huge object keeps it alive.
  • Outer properties are not the closure: w.cash = 9999 adds a property on the returned object; the private cash inside the scope is untouched.
  • Every callback is a closure — event handlers, .then, setTimeout — which is why a handler can still "see" variables from where it was defined.
  • Debounce/state utilities depend on closure memory — if the inner function didn't remember timer, debouncing couldn't work.

3.Practice — answer before you click

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "A closure is a function bundled with the scope it was created in — the inner function keeps the outer function's variables alive after the outer call returns. Classic example: a counter factory returns an inner function that increments a private count, and each call to the factory produces a separate, independent counter. I've used this for private state and for utilities like debounce, where the inner function must remember a timer between calls. One trade-off: captured variables can't be garbage-collected while the closure lives."

Definition → example → real use → trade-off. That four-beat structure is what makes the answer sound senior.
