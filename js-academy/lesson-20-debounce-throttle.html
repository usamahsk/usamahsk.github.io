Debounce & Throttle

The two function-rate-limiters every codebase has written at least once — and every interview asks about.

2 · Watchthem race
3 · Practiceget checked
4 · Provesay it out loud
In plain words Debounce = "wait until things go quiet, then act once" — like a security guard who only announces "all visitors left!" after the doorway has been empty for 2 seconds. Throttle = "act at most once per time window, no matter how many requests come" — like a checkpoint that lets one car through per minute. Both are functions that wrap your function and control when it's allowed to run.

1.Read the concept

Why they exist at all

Some events fire far more than any code can afford. A search box fires on every keystroke — type "javascript tutorial" and that's 19 API calls, most for half-finished words. Scroll fires dozens of times per second. Resizing fires continuously. The naive handler melts the network or the layout engine. The fix isn't doing less work — it's controlling how often the work is allowed to happen. That's all debounce and throttle are: gatekeepers in front of your function.

Debounce — wait for quiet

function debounce(fn, wait) {
  let timer;                              // remembered between calls — a CLOSURE
  return function (...args) {
    clearTimeout(timer);                  // cancel the previous attempt
    timer = setTimeout(() => fn(...args), wait);
  };
}

const search = debounce(q => api.search(q), 400);
input.addEventListener("input", e => search(e.target.value));
// typing "javascript" fires the API ONCE — 400ms after the last keystroke

Read the mechanism, because it's your closure lesson in action: every keystroke cancels the previous timer and starts a new one. Only when the user pauses longer than 400ms does a timer survive to completion — and the function runs exactly once, with the latest value. Debounce answers the question: "what's the final state?"

Throttle — once per window

function throttle(fn, limit) {
  let ready = true;
  return function (...args) {
    if (!ready) return;                   // window closed? drop the call
    ready = false;
    fn(...args);
    setTimeout(() => { ready = true; }, limit);
  };
}

window.addEventListener("scroll", throttle(updateHeader, 200));
// scrolling fires hundreds of events — updateHeader runs ~5 times per second

Throttle doesn't wait for quiet — it guarantees a minimum gap between runs, dropping everything in between. It answers: "keep me updated, but not more often than X." You lose intermediate events on purpose — for scroll position or progress bars, the latest-by-a-few-hundred-ms is fine.

Choosing — the interview's real question

Search box, autocomplete, form validation, resize-and-recalculate-layout → debounce: you only care about the final state. Scroll handler, mouse-move tracking, progress updates, preventing button double-clicks → throttle (or debounce-with-leading-edge): you need continuous feedback at a capped rate. Saying "debounce waits for quiet; throttle enforces a rhythm — I pick based on whether I need the final state or continuous updates" is the complete answer.

Exceptions & traps — the complete list

  • Debounce loses the intermediate calls entirely — if the user typed 10 letters, the first 9 never invoke fn. For inputs where every state matters, that's wrong: throttle instead.
  • The timer lives in a closure — remove the let timer and every keystroke schedules its own run: no debouncing at all. (A favorite "spot the bug" exercise.)
  • this and arguments must be forwarded — the wrapper uses function (...args) and fn.apply(this, args)-style forwarding; arrow-wrappers lose this.
  • Debouncing an async action doesn't cancel in-flight requests — two searches 500ms apart can still race; debounce the *triggering*, and also ignore stale responses (a response-token check).
  • Throttle drops, debounce delays — neither queues. If every event matters, neither tool is right; buffer the events yourself.
  • Leading vs trailing edge — throttle can run immediately on the first call (leading) or at the end of the window (trailing), or both. Buttons want leading; scroll wants trailing.
  • Don't debounce events that need every sample — keylogging, analytics per-interaction, game input: rate-limiting destroys the data.
  • Cleanup matters — a pending debounce timer still fires after its component dies; keep a handle and cancel on teardown (memory lesson).

4.Prove it

Your interview answer — rehearse out loud, recorded, no notes "Both are rate limiters built by wrapping a function. Debounce delays execution until calls have stopped for N milliseconds — each new call cancels the previous timer, which it remembers through a closure — so I use it where only the final state matters: search-as-you-type, autosave, resize recalculation. Throttle guarantees at most one execution per window, dropping the in-between calls, for continuous feedback: scroll, mousemove, progress. I pick by intent — final state means debounce, capped updates mean throttle. I also know the caveats: the timer lives in a closure, arguments and this must be forwarded, debouncing doesn't cancel in-flight requests, and leading-vs-trailing edge decides whether the first call fires immediately."

Definitions → mechanism (closure!) → choosing rule → caveats. And the killer detail: you can build debounce from memory, live, because you understand the closure inside it.
